## A. Native Flutter Motion — what's actually already built

A full codebase audit (not a guess) found the app's entire motion system today is built on Flutter's own SDK — zero third-party animation packages except `confetti` for celebrations. Exact inventory:

**5 `AnimationController`s** (all continuous/looping or one-shot, hand-rolled):
| File | Drives | Duration |
|---|---|---|
| `curriculum_map_screen.dart` | Pulsing "أنت هنا" glow on the current map node | 1100ms, `repeat(reverse:true)` |
| `adhkar_category_screen.dart` | One-shot golden `TweenSequence` glow when a dhikr repeat-count hits zero | 700ms, one-shot |
| `worship_coach_screen.dart` | Pulsing "التركيز الآن" focus badge | 900ms, `repeat(reverse:true)` |
| `widgets/loading_view.dart` | App-wide reusable loading spinner's breathing icon | 1100ms, `repeat(reverse:true)` |
| `widgets/animated_banner.dart` | Continuous marquee scroll of the home promo caption | 12s, `repeat()` linear |

**1 `TweenSequence`**: the adhkar golden-glow flash above — `Tween(0→1, easeOut, weight 25)` then `Tween(1→0, easeIn, weight 75)`.

**1 `TweenAnimationBuilder`**: `NavTile`'s staggered grid entrance (550ms, `Interval` + `easeOutCubic`, per-tile delay `= (index*0.06).clamp(0, 0.5)`).

**14 implicit-animation widgets** (`AnimatedContainer`/`AnimatedOpacity`/`AnimatedBuilder`/`AnimatedSlide`) across `qibla_screen.dart`, `qibla_ar_view.dart`, `adhkar_category_screen.dart`, `tahfeez_playback_screen.dart`, `prayer_times_screen.dart`, `onboarding_screen.dart`, `animated_banner.dart` — mostly 200-450ms color/opacity/size transitions on state changes (Qibla-facing glow, focus-mode chrome fade, selection highlights). **Zero `AnimatedSwitcher` uses anywhere.**

**8 `CustomPainter`s**, all static or discrete-state-driven — **none currently repaint off a live ticking `Animation` value.** The path map's connecting line and the Qibla dial repaint on data/boolean change, not per-frame.

**Zero custom `PageRouteBuilder`, zero `Hero` widgets** — every screen transition is the platform-default `MaterialPageRoute` slide.

**Conclusion**: the existing motion is real but disconnected — five different one-off `AnimationController`s with different durations (700/900/1100/1100/12000ms) and no shared timing/easing vocabulary, plus 14 implicit-animation call sites each choosing their own duration ad hoc. This is the actual problem to solve, more than "we lack animation."

## B. Rive

Verified via `pub.dev` directly (not assumed): package `rive`, current version **0.14.11**, **MIT license**, supports fully offline usage via bundled `.riv` files (`RiveFile.asset()`/local loading) — no runtime network dependency, compatible with this app's local-first requirement. Built for **interactive** vector graphics: state machines driven by app state (e.g., a progress value, a boolean), not just play-once clips.

**Real advantage over Flutter native**: a Rive state machine can encode something like "this badge has 4 visual states (locked/in-progress/near-complete/done) with smooth blending between them" far more easily than hand-rolling 4 separate `AnimationController`s — genuinely useful for exactly the kind of multi-state indicators already scattered across this app (map nodes, milestone badges, prayer status dots).

**Real cost**: authoring a `.riv` file requires the Rive editor (a separate web/desktop tool, not something generated by a code-writing pass) or downloading a pre-made community asset — each community asset needs its own license check before use, same as any other external asset.

## C. Lottie

Verified via `pub.dev` directly: package `lottie`, current version **3.5.1**, **MIT license**, supports fully offline usage via `Lottie.asset()` with bundled JSON — same offline-compatible profile as Rive. Built for **play-once/looping illustrated animations** exported from Adobe After Effects (via the Bodymovin plugin) — not interactive/state-driven the way Rive is.

**Real advantage over Flutter native**: rich illustrated micro-animations (a success checkmark that draws itself, a loading illustration) that would be very expensive to hand-code as `CustomPainter`+`AnimationController` are often available pre-made on LottieFiles' community library.

**Real cost**: same as Rive — every community JSON needs its own license verification; LottieFiles' community tier mixes free and paid/restricted-license files, "available on the site" is not the same as "free to use."

## E. Recommended use cases (decision table)

| Motion need | Technology | Why |
|---|---|---|
| Page transitions, buttons, counters, progress bars, swipe, simple success states | **Flutter native** | Already the entire app; free, no asset licensing, fully interactive/theme-aware |
| A multi-state badge/indicator that currently needs several hand-rolled `AnimationController`s to fake (map nodes, milestone states) | **Rive** (when adopted) | State-machine model fits this shape better than Flutter's imperative controllers |
| A single illustrated flourish (e.g. an empty-state illustration, a one-shot celebratory motion) | **Lottie** (when adopted) | Pre-made illustrated animation, cheaper than hand-drawing one |
| Character/environment/certificate 3D | **Blender** (paused) | Needs the rig/pipeline work already scoped and explicitly deferred |

**Recommendation: do not adopt Rive or Lottie yet.** Every current use case in the app (see §A) is already served by Flutter native motion, just inconsistently. The highest-value, lowest-risk next step is formalizing the existing native system (a `MOTION_BIBLE.md` with shared duration/curve constants), not adding a new rendering technology for needs that haven't materialized yet. Revisit Rive specifically once/if the "خريطة طالب العلم" node states or milestone badges are redesigned as genuine multi-state indicators — that's the one real fit identified.

## F. Performance considerations

- Flutter native (`AnimationController`/implicit widgets): negligible cost, already proven across 71 screens.
- Rive/Lottie: both render via Skia (Flutter's own rendering engine) rather than a WebView or embedded browser — no known heavy performance tax, but neither has been benchmarked in this app since neither is installed.
- Blender-rendered assets: only ever ship as static PNG/WebP or short video — zero runtime cost, all cost is paid once at asset-creation time (already the plan).

## G. Offline/local asset requirements

All three candidate technologies (Rive, Lottie, Blender-exported) support fully local, bundled-in-APK assets with zero runtime network dependency — consistent with this app's local-first design. Confirmed directly from each package's own docs, not assumed.

## H. Licensing requirements

Every external asset (Rive community file, Lottie community file, any downloaded 3D asset) requires an individual license check before use — "available in a community library" is never sufficient on its own. This session's own Humaaans illustration check is a worked example of why: the official site claimed CC0, but the actual downloadable package's bundled `LICENSE.md` was CC BY 4.0 (attribution required) — a real discrepancy only caught by opening the actual license file, not by trusting the marketing page.

## I. Migration/maintenance cost

Adding Rive or Lottie later is additive, not a rewrite — neither replaces the existing native motion system, both would sit alongside it for the specific new use cases in §E. No migration cost for the 19 existing native-animation call sites; they stay exactly as they are.
