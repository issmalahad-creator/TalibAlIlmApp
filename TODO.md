## Phase 35 — AR Qibla bearing bug fix: gimbal lock + reversed heading (Ismail's on-device report 2026-08-16)

Ismail tested Phase 33's changes and reported two concrete regressions: "البوصلة تحتاج ان ارفع الكامرة الى الاعلى" (needed to raise the camera up for it to settle) and "انعكست" (the direction reversed). He also pasted a long, well-researched multi-layer Qibla architecture proposal (Location Engine → Qibla Calculation → Orientation Engine → Validation Engine → Qibla UI) and asked me to research online and get stronger on this specifically, since he considers it the single hardest part of the app.

**Root cause, found by working the actual rotation math rather than guessing**: `flutter_rotation_sensor`'s default `azimuth` tracks the compass bearing of the phone's **top edge** (its body Y-axis) — correct for the flat-held compass dial, but wrong for a phone held vertically like a camera. Held that way, the top-edge axis points mostly toward the sky, so its horizontal component shrinks toward zero — a near-gimbal-lock condition where tiny sensor noise swings the reported azimuth wildly, which only settles once the phone tilts back toward flat (exactly the "raise the camera" symptom). Using the wrong body axis for "which way the lens points" also explains the reversed reading.

- [x] **Fix**: `QiblaArView` now computes its own bearing directly from the orientation event's rotation matrix, using the body **-Z axis** (the direction the back camera actually looks) via `atan2(-m.c, -m.f)`, instead of the default Y-axis-based azimuth. Verified algebraically before shipping: reproduced the package's own documented default-azimuth formula from its matrix math to confirm the derivation method is sound, then re-derived for the camera-facing axis and sanity-checked it against two independent hand-worked cases (camera pointing north → 0°, camera pointing east → 90°) — not a blind guess. Held vertically, the back-camera axis is naturally close to horizontal, so it avoids the gimbal-lock zone entirely instead of requiring the user to compensate.
- [x] The compass dial tab (`_CompassView`, meant to be used flat) correctly keeps using the default Y-axis azimuth — the bug was AR-view-specific, not present in the dial.
- [x] `QiblaArView` now runs its own local orientation subscription again (reverted the earlier "share one fused heading between both tabs" design from Phase 33 — that sharing was itself part of the problem, since the two views genuinely need different axis conventions, not just different smoothing).
- [x] `flutter analyze` clean, debug APK built.
- [ ] Not yet confirmed fixed on-device by Ismail — I have no way to test the actual sensor behavior myself.

**Researched but deliberately not built this round — magnetic vs. true north declination correction**: Ismail's pasted proposal correctly flags that `adhan_dart`'s Qibla bearing is computed from pure geography (a **true-north**-relative great-circle bearing), while the device's compass heading is **magnetic-north**-relative — a real, currently-uncorrected gap on Android specifically (this app's compass tab already uses `flutter_compass`, which on iOS typically already returns `CLHeading.trueHeading`, but Android has no equivalent built-in correction). `flutter_rotation_sensor`'s own `ReferenceFrame.trueNorth` option **silently falls back to magneticNorth on Android** (confirmed by reading its own source doc comments), so it wouldn't actually fix anything on the platform Ismail is testing. The one pure-Dart declination package found (`geomag` on pub.dev) bundles **WMM-2015v2 coefficients from 2018** — over a decade stale by 2026, which could introduce its own new error rather than reliably fixing the existing one. Decided not to bolt on an unverified, stale-data package for an unverifiable (no device) fix; flagged as a real follow-up needing either fresh WMM/IGRF coefficients or a small native platform-channel call to Android's own `GeomagneticField` class, not built today.

**Confirmed already correct, in response to Ismail's proposal's core worry**: the Qibla bearing itself is calculated purely from location/geography (`adhan_dart`'s `Qibla.qibla()`, a great-circle bearing from lat/lng to the Kaaba) — the compass is only ever used to compare the device's *current* heading against that pre-computed target, never to determine the target itself. This already matches the "don't calculate Qibla from the compass" principle his proposal opens with.
