## 2. الواقع الحالي في الكود (مُحصًى)

- `CircularProgressIndicator` في **74** موضعًا، `AppLoadingView` (أيقونة + spinner + رسالة) في **58** ملفًا — كل شاشة تخترع انتظارها.
- `HapticFeedback` في 14 موضعًا فقط؛ لا حالة «ضُغط» موحّدة.
- لا منع موحّد للضغط المزدوج على التنقّل (ضغطتان سريعتان = صفحتان).
- لا skeleton في أي مكان.

## 3. مستويات التوقيت — القاعدة الحاكمة

الواجهة **لا تعرف مسبقًا** كم ستستغرق العملية؛ لذلك تُظهر التغذية الراجعة **بمؤقّتات تصاعدية** لا بتقدير:

| الزمن المنقضي | ما يراه المستخدم |
|---|---|
| 0 ms | استجابة الضغط فورًا: انضغاط 0.97 + ظل أخفض + تموّج خفيف (دائمًا، لكل عنصر تفاعلي مهم) |
| < 300 ms | لا شيء آخر — الانتقال نفسه هو التغذية الراجعة |
| ≥ 300 ms | مؤشّر صغير **داخل الزر/العنصر نفسه** (لا في منتصف الشاشة) |
| ≥ 800 ms | نص سياقي: «جاري فتح الكتاب…» (فعل + شيء، لا «Loading») |
| ≥ 2 s | «مرافق الانتظار» §6 إن كانت الشاشة كلها تنتظر؛ أو تقدّم حقيقي إن كان معروفًا |
| مهلة | ليست فشلًا: «يستغرق وقتًا أطول من المعتاد…» مع إبقاء العملية حيّة + زر إلغاء إن كانت قابلة للإلغاء |
| فشل | «تعذّر فتح الكتاب» + سبب مفيد إن وُجد + [إعادة المحاولة]؛ التفاصيل التقنية في السجل فقط |

## 4. آلة حالات الفعل — `TalibAction`

```
idle → pressed → running(elapsed) → success → idle
                     ├→ failed(reason) → idle (retry)
                     ├→ cancelled → idle
                     └→ superseded (فعل أحدث لنفس الهدف ألغاه)
```

- **`ActionKey`** (مثل `open_book:123`، `save_note`، `play_audio`) — مفتاح عدم التكرار: ضغطات لاحقة على نفس المفتاح أثناء `running` **تُدمَج** في نفس العملية (نفس مبدأ `BootScheduler.ensure`).
- **مكوّنات صغيرة معيارية، لا «God object»:**
  - `TalibPressable` — استجابة الضغط الموحّدة (انضغاط + ظل + تموّج + اهتزاز خفيف اختياري من الإعدادات، مُطفأ افتراضيًا).
  - `TalibActionButton` — زر يعرض حالته: `حفظ` → `◌ حفظ…` → `✓ تم الحفظ` → `حفظ`؛ لا يبدو ميتًا، ولا يقبل تشغيلًا مزدوجًا.
  - `talibPush(context, key, builder)` — تنقّل مُزال التكرار (نفس الهدف خلال 600 ms = انتقال واحد) بانتقال موحّد (تلاشٍ + انزلاق خفيف RTL-aware).
  - `ContextualLoading` — يحلّ محل `AppLoadingView`: يطبّق جدول §3 بنفسه (لا يظهر شيئًا قبل 300 ms).

## 5. الهيكل قبل المؤشّر

حين يكون شكل المحتوى معروفًا (قوائم الكتب، بطاقات الرئيسية، نتائج البحث، صفحة كتاب): `TalibSkeleton` بنفس تخطيط المحتوى الحقيقي، وميض بطيء هادئ (≥1.6 s للدورة)، يُستبدل بالمحتوى بتلاشٍ دون قفزة في التخطيط. **لا skeleton لانتظار < 300 ms.**

## 6. «مرافق الانتظار» — انتظار جذّاب ومتنوّع (فكرة أصيلة لطالب العلم)

الفكرة: **الانتظار الطويل (≥ 2 ث) لحظة فائدة لا لحظة فراغ** — تطبيق مباشر لمبدأ «الوقت المشغول أقصر» — لكن بمحتوى **موثّق من بيانات التطبيق نفسها**، لا نكتًا ولا إحصاءات مخترعة:

| النوع | المصدر الموجود أصلًا | مثال |
|---|---|---|
| ذكر قصير مع فضله | حصن المسلم (`adhkar_items`) | «سبحان الله وبحمده…» |
| حديث من الأربعين (سطر + راويه) | `nawawi_hadiths` | «إنما الأعمال بالنيات» |
| فائدة من آية | `quran_note` (Quranpedia notes) منسوبة لقائلها | — |
| كلمة قرآنية ومعناها | الغريب (`meanings`) | — |
| سؤال مراجعة خفيف مما حفظه المستخدم | محرك المراجعة القائم | «أكمل: الحمد لله رب…» |

**قواعد:** يظهر فقط بعد 2 ث (لا يؤخّر عملية سريعة أبدًا)؛ **يتناوب ولا يتكرر** (ذاكرة آخر N عرضًا محليًا — نفس فكرة «recency penalty» في نظام إشعارات Duolingo، بلا AI)؛ يختفي فور انتهاء العملية حتى لو في منتصف الجملة (الفائدة لا تحبس المستخدم)؛ كل عنصر يحمل مصدره؛ لا يظهر فوق المصحف (قاعدة «المصحف مقدّس»).
**الأشكال البصرية تتنوّع حسب السياق** — نفس اللغة، أشكال مختلفة: خط ذهبي بنقطة ضوء (البداية)، ريشة تكتب سطرًا (الكتب)، هلال يمتلئ بالتقدّم الحقيقي (التنزيلات)، نبضة على الشجرة (شجرة أصول التفسير) — حركات رخيصة بـ`CustomPainter`، بلا Lottie.

## 7. حالات خاصة

- **البحث:** الاستعلام يبقى ظاهرًا، مؤشّر رفيع تحت الحقل بعد 300 ms، النتائج تحلّ محل القديمة بلا شاشة فارغة.
- **الصوت:** ▶ → ◌ (فورًا) → ⏸؛ نص «جاري تجهيز الصوت…» بعد 800 ms فقط.
- **السحب للتحديث:** الصفحة تبقى، المؤشّر في مكانه القياسي.
- **الرجوع أثناء حفظ:** «جاري حفظ التغييرات…» ثم خروج — لا صفحة تبدو متجمّدة.
- **زر معطَّل:** يقول لماذا («جاري تجهيز الصوت…») لا رمادي صامت.
- **الإذن:** لا طلب إذن نظام بلا شاشة تمهيد تشرح السبب (مثلًا بطاقة «فعّل أوقات الصلاة» — راجع ZW-4).

## 8. إمكانية الوصول

كل حالة = شكل + نص، لا لون وحده (✓ + «تم الحفظ»، ! + «تعذّر…»، مؤشّر + «جاري…»). `Semantics(liveRegion: true)` لرسائل الحالة ليقرأها قارئ الشاشة. تحترم «تقليل الحركة» في النظام (`MediaQuery.disableAnimations`).

## 9. الأداء

كل التغذية الراجعة: `AnimationController` واحد لكل مكوّن، `RepaintBoundary` حول المتحرّك، لا blur ثقيل، لا ظلال ضخمة، لا Lottie، هدف 60 FPS. `ContextualLoading` لا يبني شيئًا قبل 300 ms (صفر كلفة للعمليات السريعة).

## 10. مصفوفة الاختبارات

ضغطة واحدة · ضغطتان · ضغطات متتالية سريعة (دمج) · تنقّل سريع (لا مؤشّر) · تنقّل بطيء (مؤشّر بعد 300 ms، نص بعد 800 ms) · تنقّل فاشل · ملغى · عملية DB طويلة (مرافق الانتظار بعد 2 ث، يختفي فور الانتهاء) · بحث سريع/بطيء · حفظ · حذف · تجهيز صوت · رجوع أثناء التحميل · التطبيق إلى الخلفية أثناء عملية (لا setState بعد dispose). كلها `testWidgets` بساعة مزيّفة (نفس نمط `test/brand_splash_test.dart`).
